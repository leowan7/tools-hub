# Competitor teardown: ariax.bio (2026-09-24)

Method: logged-in walkthrough in Chrome. Covered marketing site, pricing, docs index,
resources index, dashboard, target-prep tool, BoltzGen setup, BindCraft2 setup, API keys,
team, billing. NOT covered: a live run, the project detail page, or any results view —
launching a job spends money, so everything below the "Start" button is unverified.

## What they have that we do not

### 1. Target prep is a free, standalone, pre-run step
A dedicated page, reachable before any project exists and before any spend, that:
- loads a structure by upload OR by RCSB **keyword** search with an autocomplete list of
  hits and their titles (we accept an ID; they let you search "PD-L1")
- lists chains as checkboxes and shows the per-chain sequence
- takes per-chain binding and not-binding residue masks, plus a "bind anywhere" toggle
- has a 3D picker where clicking a residue adds it to the mask
- reports original vs trimmed residue count and a plain verdict that the trimmed target is
  a suitable size for the chosen engine
- exports the trimmed file, or hands the prepared state directly to the run form

This is our preflight panel's job, but theirs is a destination rather than a validator that
fires after you have already filled a form.

### 2. They surface input normalisation instead of hiding it
The prep step printed, in a log the user can read, that residues had been renumbered to a
canonical 1-based scheme per chain, that a ligand had been moved to its own chain, and that
SEQRES had been synthesised so indexing stays stable across gaps. The run form repeated the
index shift with before/after numbering per chain.

This is the single most relevant thing on the site for us. Our recurring defect class is
exactly this: contigs that must cover the chain, bare hotspot numbers steering the wrong
protomer, two-line DBREF records, author vs canonical numbering. We fix these in code and
say nothing. They make the remap visible, which both builds trust and lets a user catch a
wrong chain before paying.

### 3. Navigation is by what you want to make, not by which tool makes it
The left rail lists binder formats — Fab, scFv, VHH, large binder, miniprotein, ankyrin
repeat, peptide, cyclic peptide, helicon. Choosing one routes to whichever engine supports
it, with that engine's defaults preselected. Engine choice becomes an implementation detail.

This is our "help me choose a tool" milestone, and they solved it with information
architecture rather than a questionnaire. Worth weighing against the two-question chooser
we scoped: theirs needs no rules table and no maintenance, but it hides the comparison when
two engines both serve a format.

### 4. Validate before you spend
The setup form has a "Validate Settings" button distinct from "Start", plus an always-on
log panel inside the form. Our preflight is coupled to submission.

### 5. Cost controls are in the submit form
- pick which GPU models are acceptable, split into high-availability and premium/limited
- a cost-versus-performance preference ranking, and a turbo (parallel) mode
- a live estimated hourly range that responds to those checkboxes
- an explicit budget cap field
- "number of final designs" separated from "maximum trajectories", with copy explaining that
  final designs are accepted candidates and trajectories cap attempts including failures

That last distinction is one we have struggled to express in our own guides.

### 6. Pricing page does the arguing for them
A published per-GPU-hour table for twelve GPU models, each with VRAM, their rate, an
approximate major-cloud rate, and the percentage difference — including rows where they are
at parity and rows where the comparison is "not widely offered". Plus a small interactive
calculator (pick GPU, pick runtime, see both totals) captioned as illustrative. No
subscription, no quota request, billed on elapsed runtime, prorated.

Publishing the parity rows is what makes the cheaper rows credible.

### 7. Account plumbing we lack
- API keys scoped as view-only versus full, described as being for the CLI, scripts and
  coding agents, with an expiry
- teams with shared credit balance and a join-by-slug request flow
- automatic top-up below a threshold, and self-serve purchase-order quote generation
- a paid-consulting ladder (target prep, configuration, monitoring, post-run analysis)
  quoted separately from compute

### 8. Content cadence
Roughly seventeen posts across news, tutorials and opinion, filterable and sortable. Each
engine launch gets an announcement; there is a recurring "getting started with X" tutorial
series, and a separate target-preparation tutorial. Docs are numbered chapters with a
per-page table of contents, one chapter per engine setup page.

## What we have that they appear not to

Stated from our own repo and memory, not from their site:
- derived pass/fail verdicts and score legends at render time
- per-design developability and interface triage
- an epitope-scoring entry point
- a refusal/observability layer around anonymous use
- recorded-run runtime anchors behind our estimates

## Recommended, in priority order

1. **Make the numbering remap visible.** A short, plain-language note wherever we renumber,
   re-chain, or synthesise records, naming the before and after. Cheapest item here and it
   attacks our worst defect class directly.
2. **Promote preflight into a free standalone target-prep page** with RCSB keyword search,
   chain and residue selection, hotspot picking, trimmed download, and a hand-off that
   carries state into any tool's form.
3. **Split "Validate" from "Run".**
4. **Add a format-first entry to the catalog** — decide whether it replaces or complements
   the two-question chooser before building either.
5. **Publish the rate table**, parity rows included, with the runtime calculator.
6. **Scoped API keys and team-shared balance** — the first is small, the second is not.

# Addendum: dashboard and visual design

Method note: their dashboard and setup pages were viewed logged in. Our public catalog and
home were viewed live; our logged-in jobs list was NOT viewed — I declined to sign in — so
that half is read from `templates/jobs_list.html` rather than seen.

## Shell

**Theirs.** A persistent left sidebar is the spine of the app, grouped under four headings:
Home, Plan, Design, Manage. Every binder format is its own icon-and-label row, so the whole
product surface is visible without clicking. It collapses. A persistent top bar carries the
credit balance, a refresh control, an "Add Credits" button, the account email and sign-out.
Wherever you are, you can see what you can spend and how to spend more.

**Ours.** No sidebar anywhere. A single top nav with five items, and the tools live behind
"All tools". Depth is reachable only by navigating into it. We do show a wallet balance in
the nav when signed in, but there is no always-present path back to the rest of the product.

The sidebar is the biggest structural difference, and it is why their app feels like an
application and ours feels like a set of pages.

## Dashboard proper

**Theirs.** Four stat cards across the top — active projects, completed projects, GPU hours
used, proteins designed — then Ongoing/Completed tabs over a paginated table whose columns
are project name, created, protocol, type, status, GPU instance, cost per hour, run time,
progress and actions. The table scrolls sideways at this width, which is a real flaw.

**Ours.** A heading, a subtitle, one panel, one table: job, tool, preset, status, submitted.
No aggregate row, no cost, no runtime, no progress. A job that is running looks the same as
one that finished an hour ago except for a badge.

**Where we are better.** Our empty state is genuinely good — it names the wallet balance and
lays out a three-step ladder to a first run. Theirs shows four zeros and an empty table,
which tells a new user nothing. We also have compare-selected checkboxes on succeeded jobs,
which they have no equivalent of.

## Setup pages

Theirs are long accordions. Every section collapses, most collapsed sections carry a
one-line summary of their current state ("Using defaults"), nearly every label has an
information tooltip, a submission summary condenses the whole form to one sentence, and a
log console sits pinned under the form reporting what the backend did to the input. The 3D
viewer is inline in the page flow at a generous size, not in a modal or a side panel.

Ours are flatter forms with a preflight panel that fires late.

## Look

Theirs is a conventional navy dark-mode SaaS: blue accent, blue section headings, system
sans throughout, icon per nav item. Competent, unremarkable, immediately legible as a
developer tool.

Ours is the dark editorial direction — serif display, green accent, more considered
typography, better copy. On the marketing pages that is a clear win; our catalog groups
tools by the question a scientist is asking rather than by product name, which reads far
better than their flat format list.

Inside the app the advantage inverts, because the editorial styling never got applied
there. `templates/jobs_list.html` is carrying inline styles on almost every table cell,
which is what happens when a page is built without a component to build it from.

## What to take, in order

1. **A persistent left sidebar in the signed-in app**, grouped the way our catalog already
   groups tools by intent. This is the change that would most alter how the product feels.
2. **Columns that answer "what is it doing and what has it cost"** on the jobs table —
   runtime, spend so far, progress. We hold all three already.
3. **Collapsed sections that state their own summary** on the long setup forms.
4. **A visible log panel** on the run page, which is also where the numbering-remap notes
   from the main teardown belong.
5. Stat cards are the least valuable item here. Four zeros is worse than nothing, and our
   empty-state ladder already beats them. Add them only once a user has history.
